1What Codemare is, and how the goal moved

Today: a DSA practice and learning platform. Learners solve problems in an in-browser editor in Python, JavaScript, TypeScript, C++, Java or Go; a sandboxed judge times the function alone on the CPU clock, in microseconds; and a tiered learning loop turns first solves into topic tokens, tokens into unlocked topics through recipes, and timed gate exams into open tiers. Three Learn tracks, profiles and 17 badges, question authoring, a hidden algorithms library and a Directus admin sit around it, all on one VPS.

The goal moved four times, and each move explains a chunk of the codebase.

The latest move: from a judge to the learning platform

On 28 September 2026 the goal moved from “a judge behind a login wall” to the full platform in the design project's brief, copied verbatim into docs/spec/implementation-prompt.md: a catalog and editor, a learning loop of tokens, recipes and gates, Learn tracks, profiles and badges, authoring, a hidden library, a Directus admin, and a one-VPS deploy with backups. Two things shaped how it was built:

  • The design files never arrived. The brief builds from /design/tokens.css, MVP Architecture.html and the screen artboards; none were in the repository. Rather than stall, the build ran against a reconstructed spec, docs/spec/architecture.md, with the already-ported design system as canonical, and wrote down every place it departs from the brief (decision 15).
  • It was built by agents working in parallel: four phases, each a set of agents in their own git worktrees with strict file ownership, an integrator verifying and merging every branch, and CI as the final word (decision 36). From the spec commit (4ce8b73, 14:58) to the last merge (e746e6d, 01:57 the next night): 106 commits, 13 merges, about eleven hours.

2System at a glance

Three things hold state or run code, and they trust each other as little as possible. web/ owns identity, content and every user record: it is the only thing the browser talks to and the only writer of app.*. backend/ owns execution: take code plus tests, run them in a sandbox, stream the results. It has no database, no users, no sessions, and doesn't know who you are — deliberately (decision 06). Postgres holds both schemas, and Directus edits content rows through a database role that can do nothing else (decision 26).

Ports (production)

Keeps state
Postgres (app, content, directus), the backups; the compile service keeps only caches (compiled artifacts, the Go build cache)

Decision 01 · current

Replace Docker with isolate

Situation

The original executors ran each submission in a Docker container. Timing was wrong — container startup (hundreds of ms) dwarfed the algorithm — and "very accurate" was a hard requirement.

Options
  • Keep Docker, subtract a measured baseline.
  • Firecracker / gVisor micro-VMs.
  • isolate — the IOI contest sandbox (namespaces + cgroups v2), used by real judges.
  • No sandbox.
Choice

isolate. It boots in about a millisecond, meters CPU time and peak memory via cgroups, writes a machine-readable meta file, and is what competitive-programming judges already trust. Firecracker was overkill for a single VM; subtracting a Docker baseline is guesswork.

Consequences

Linux-only in production (macOS dev needs the local adapter, decision 04). Per-submission overhead dropped from ~300 ms to a few ms. Limits live in backend/src/config/sandbox.ts and languageSpec.ts; memory is a cgroup cap (--cg-mem), not an address-space rlimit (section 6):

PhaseCPU timeWall timeMemoryPIDsLargest file
run10 s (callers may lower)2× CPU256 MB (callers: up to 512)per language, 1–6416 MB
compile15 s30 s512 MB16; javac, go build 6464 MB
Decision 02 · current

Measure the algorithm, not the process

Situation

Even with a 1 ms sandbox, "time" for Python included interpreter startup (~20 ms) — useless for comparing O(n) against O(n log n) on small inputs.

Choice

Two clocks, reported separately.

  • runUs — measured inside the user process, around the function call only, on a CPU clock (per language in section 3): the thread's own clock where the runtime has one (Python, C++, Java), process-wide in Node and Go. A CPU clock stops ticking while the process is descheduled, so other load on the host cannot inflate it. A submission's runtime is the sum over its tests.
  • wallUs per test (elapsed wall clock for the same call) and compileMs — kept as diagnostics. Compile time is never charged to the user.

Measured on a 10-core machine with 20 busy loops running: wall time per call rose 2.0–2.6× while CPU time moved 7–16% across two runs (d332efb) — the residual is cache pressure and clock frequency, which host tuning (dedicated vCPUs, performance governor) addresses at deploy.

Memory follows the same idea: tracemalloc peak (Python), heap delta (JS/TS), bytes allocated during the call (Go), whole-process peak RSS (C++, on the verdict only), none for Java — JVM heap is too noisy per call.

Lesson

The sandbox can only meter the whole process; the harness is the only place that can meter the algorithm. Both numbers are needed, and they answer different questions.

Decision 03 · current

Fairness: one core, tight PID caps

Situation

With accurate timing, the next question is whether a user can cheat it by parallelizing — and whether one learner's threads can take CPU from everyone else's boxes.

Choice

Every run box gets exactly one CPU. The compile service plans it (cpuPinning.ts): run box N goes to CPU N mod k, round-robin over the CPUs the service may use, and with four or more CPUs the first one is kept free of boxes for the API. Compile boxes run trusted compilers, not learner code, and may use every box CPU. ISOLATE_CPU_PINNING=off switches pinning off.

An affinity mask alone is only advice — a program can widen its own with sched_setaffinity(2), one RawSyscall in Go — so pinning is applied twice. The adapter starts every isolate run under taskset -c, and the container entrypoint writes the same plan into isolate's config as per-box cgroup cpusets (box<N>.cpus), which a program cannot leave. At startup the service tries to widen a box's mask from inside it and logs whether pinning is enforced (cpuset), only advisory (taskset without cpusets, e.g. a host whose isolate config has none) or missing. CI's isolate smoke runs four spinning threads in Java and four goroutines in Go (after a widening attempt) and requires CPU time ≈ wall time.

PID caps are defense-in-depth and a fork-bomb stop, set per language to what the runtime itself needs (languageSpec.ts):

LanguagePID capWhy
C++1Truly single-threaded; std::thread is denied
Python1GIL anyway; blocks multiprocessing
JavaScript, TypeScript16Node needs ~7 threads just to boot (libuv pool, V8 GC)
Java64The JVM spawns ~25 internal threads (GC, JIT, finalizer…)
Go16The runtime needs a few threads (sysmon, GC); GOMAXPROCS=1 by default
Consequences

Parallelism buys neither wall time nor other learners' CPU: measured under isolate, four busy threads burn 1.00× CPU per wall second pinned and 3.95–4.00× unpinned, and the CPU-time limit counts every thread. Pinning does not change what a timing measures, though: the Java harness reads the calling thread's CPU clock, so work handed to another thread is missing from its runUs, pinned or not.

Lesson

This decision was first implemented as isolate's --core=N — the core-dump size limit, not a core. Boxes got up to N KB of core file and no pinning at all, until the image started pinning boxes on its own. Every box now runs with --core=0. A sandbox guarantee has to be checked from inside the sandbox, not read off a flag name (section 6).

Decision 04 · current

Two adapters: isolate in production, local in development

Situation

isolate doesn't run on macOS, and development happens on macOS.

Choice

A SandboxAdapter interface with two implementations. Selection is automatic (isolate present → use it), overridable with SANDBOX_MODE.

Consequences

Development works anywhere and the harness-level timing is still real. The price: anything specific to isolate is untestable locally. That gap bit us (the Java *.class glob, section 6), which is why CI now builds the production image and runs a 26-check isolate smoke on every push (decision 35).

Decision 05 · current

Compile cache and parallel IDE cases

Situation

C++ compile is ~500 ms; users re-run unchanged code constantly; IDE mode ran its test cases one after another.

Choice

A content-addressed compile cache keyed on sha256(language + compiler argv + source), single-flight (concurrent identical compiles wait for one), bounded LRU of 256 entries, shared by both adapters, for C++, Java and Go. A cache hit emits no compiling event. IDE test cases run in parallel.

Result

About 10× faster C++ re-runs; about 4× faster multi-case IDE runs. The bound is an entry count, not bytes on disk — a known gap (section 7).

Decision 06 · amended by 17

Split into two services with an internal token

AmendedThe split and the token stand. What changed is what the compile service knows: it used to hold the problem catalog (backend/src/data/problems/*.json) and judge by problem id; since decision 17 the caller sends code and tests, and the service keeps no content at all.

Situation

The original monolith mixed "run untrusted code" with "manage users". Those have opposite scaling and security profiles.

Choice

backend/ became a stateless compile service; web/ holds everything user-facing. They share one secret, INTERNAL_TOKEN, sent as X-Codemare-Token and compared timing-safely. The token lives only in server code (web/lib/compile.ts is server-only), never in the browser — and, since decision 29, never inside a sandbox either.

Rules
  • Dev with no token set is "open" — but production with no token throws at boot on both sides; the web guard also rejects placeholder values.
  • The compile service is identity-blind. It can be scaled or swapped without touching auth; per-user limits live in the web app (decision 32).
  • CORS is effectively moot (server-to-server); kept for the legacy alias.
Decision 07 · amended by 17

An optional Redis queue, not a mandatory one

Amended/v1/run and /v1/run/stream always run inline, never through the queue, so the web app's judging doesn't use it. The queue now serves only the legacy /v1/execute and /v1/ide/execute; the web app's IDE client still handles a 202 {token} transparently. Scaling judging past one host would need the streaming path to learn the queue.

Situation

Burst load — a class submitting at once — would pile onto a single VM.

Choice

BullMQ over Redis, gated entirely on REDIS_URL. Unset → everything is synchronous, exactly as before. Set → POST /v1/execute returns 202 {token} and the client polls, or forces sync with ?wait=true. Workers run as a separate process (npm run worker) or inline (WORKER_INLINE=true) for a single-VM deploy. GET /v1/queue/stats exposes depth for tuning.

Why optional

One VM handles the first thousand users; forcing Redis on day one adds an operational dependency for nothing. Turning it on later is a config change.

Decision 08 · amended by 17

Next.js App Router with server actions

AmendedRuns no longer go through a server action: /api/run, /api/submit and /api/build are route handlers, because they stream (SSE) and must answer 401/403/409/413/429 as JSON before the stream opens. /api/hints and /api/ai-review are JSON route handlers. Server actions remain for everything that returns once. The old runSolution action is gone.

Situation

The Vite SPA would have needed its own API layer to hold sessions and call the compile service without leaking the token.

Choice

Next.js 15 App Router, server components by default. Server actions — signUp, runIdeCode, unlockTopicAction, publishAction and friends — run on the server, hold the token, and call the domain layer; route handlers do the same for streams. Monaco for the editor; design tokens as CSS variables ported component by component from a Claude Design bundle.

Consequence

There is no public API for the browser to call: the middleware walls everything under /api except /api/auth (a signed-out call gets 401 JSON), and every handler and action re-reads the session itself.

Decision 09 · amended by 31

Auth: email/password on Postgres, JWT sessions, a login wall

AmendedThe single /auth page became /signin, /signup, /forgot and /reset (/auth redirects). The JWT now carries the role and handle, the routing rules are a pure, tested function, password reset exists (hashed, single-use, 30-minute tokens), and the middleware runs on an Edge-safe config (decision 31).

Situation

The pivot to a content platform needs identity. OAuth alone blocks anyone without a GitHub/Google account and needs client IDs to even test.

Choice

Auth.js v5 with a Credentials provider — bcrypt (cost 12), minimum 8-character passwords, sign-up as a server action — plus GitHub/Google when configured. JWT session strategy (no session-table round-trip per request). A middleware login wall: every page except the auth pages redirects signed-out visitors to /signin?next=…, and signed-out API calls get a 401.

Consequence

Self-hosting requires trustHost: true, and this is where the worst bug of the project hid (section 6).

Rate limits

Every entry point is throttled in-process (web/lib/rateLimit.ts, sliding window): sign-up 5 per hour per IP; login 10 per 15 min per IP and 5 per 15 min per email, counted before the bcrypt compare and reset on success; reset requests 5 per 15 min per IP and, silently, 3 per hour per email. Over the limit, authorize() throws a CredentialsSignin with code rate_limited so the form can say so. In-memory is correct for one instance; a multi-instance deploy swaps in Redis behind the same consume().

Decision 11 · amended by 18, 19

Generate C++/Java harnesses from a typed signature

AmendedGo joined C++ and Java with the same approach (decision 19). The generated program no longer prints one JSON document at the end: it writes one marked line per test, and the service — not the harness — compares outputs, with a 1e-6 tolerance for doubles (decision 18).

Situation

Python and JS harnesses can call f(*args) on JSON values. C++ and Java are statically typed; the harness must know that nums is a std::vector<int> before it can compile.

Options
  • Hand-write a harness per problem — doesn't scale to user-authored content.
  • Parse JSON at runtime in C++/Java — needs a JSON library inside the sandbox; slow and fragile.
  • Give each problem a typed signature and generate the program with test data embedded as typed literals.
Choice

The third. Questions declare their parameter and return types from int, long, double, bool, string, char and their [] / [][] forms; the generator does the rest.

Convention

Content authors must follow this or the harness cannot compile the submission (the authoring editor generates compliant stubs):

  • C++: a free function ret name(params), no main, no includes needed — the harness provides the full standard header set.
  • Java: class Solution { public static ret name(params) { … } } — not public class, and the method must be static.
  • Go: a bare func, no package clause; imports are hoisted and merged by the service.
JVM limit

Java caps a method at 64 KB of bytecode; a 10 000-element test literal in main() blew it. The generator now emits one method per test and chunks large literals.

Decision 12 · current

Verdicts are derived, never echoed

Situation

The sandbox reports OK whenever the process exits 0 — which a wrong answer does. For a while, failed submissions were stored and shown as "Accepted".

Choice

The compile service derives the verdict from its own evidence (runService.ts, deriveVerdict in validationService.ts). The web app adds two checks before persisting: OK is recorded only if every test passed, and a stream that didn't report every test becomes XX.

Decision 13 · current

Order-insensitive judging via compareMode

Situation

Two Sum says "return in any order", but the judge compared [0,1] to [1,0] and failed correct solutions.

Choice

An optional per-question compare_mode: "unordered": arrays are compared as multisets by sorting both sides on a canonical JSON key, recursively — children are canonicalized before the parent is sorted, so [[3,1],[0,2]] equals [[1,3],[2,0]]. The service does the comparison (decision 18). The default stays ordered. Set it only when the statement promises any order.

Decision 14 · superseded by 35, 36

Process: dev → QA → manager agents, then CI on Linux

SupersededThis describes the process up to September 2026. The platform was built by phased parallel agents in separate worktrees with an integrator verifying every merge (decision 36), and CI now runs six jobs, including the isolate smoke and Playwright against a production build (decision 35). The numbers below are as they were then.

Situation

With one human, self-review misses what an adversarial second reader catches.

Choice

Work is split across agents with separate contexts: a dev agent implements and self-verifies; an independent QA agent tries to break it against a written test plan and files P0–P2 defects; a manager triages, routes fixes, and commits only after a re-verification pass. Then GitHub Actions runs on every push.

Why it earned its keep

QA found 13 defects the developers' own verification missed, including two P0s; the cross-product QA pass (new problems × new languages) found the JVM limit; CI on Linux found the header bug.

Context

Decision 16 · new

Keep our compile service instead of self-hosting Judge0

Context

The brief's stack names self-hosted Judge0 for execution. Codemare already had a compile service on isolate — the same sandbox Judge0 wraps — with CPU-clock timing of the function alone, per-language PID caps, one CPU per box, a compile cache and an optional queue (decisions 01–07).

Options
  • Judge0: another server with its own workers and database on the one VPS; whole programs judged against stdin/stdout, the process timed rather than the function.
  • Extend our service.
Decision

Extend ours, recorded as the spec's first deviation. The extensions: the pure-executor contract with SSE (17), per-test result lines (18), TypeScript and Go (19), dependency preludes (25), and the hardening in 29.

Consequences

Timing stays per call on the CPU clock — the thing decision 02 exists for — and harnesses call the learner's function with typed arguments, so statements need no I/O boilerplate. The price is that we own the sandbox's security and must prove it, which is what the 26-check isolate smoke in CI does.

Decision 17 · new · supersedes the backend catalog

The compile service becomes a pure executor: code and tests in, SSE out

Context

Content was moving into Postgres (21) and authors would write questions the compile service had never seen. The service still read problems from backend/src/data/problems/*.json by id (/v1/problems, /v1/execute), answered with one JSON document, and polled when queued.

Decision

POST /v1/run takes everything from the caller — code, an optional prelude, the function name, the signature, the compare mode, the tests with their expected values and hidden flags, and limits — and keeps no state about questions. POST /v1/run/stream is the same run as Server-Sent Events: queued (only while waiting for a box), compiling (only for a real compile), running, one test per test in index order, then verdict; a heartbeat every 15 s; a disconnect aborts the run. Validation is strict because the endpoint is now a trust boundary for data as well as code: 64 KB of code, 256 KB of prelude, 1–200 tests within 4 MB, every value checked against the signature (an int is 32-bit), unknown keys refused so a misspelt option can't be silently ignored — all a 400 before any stream opens. The web app relays the stream to the browser in its own protocol (section 5).

Consequences

One service now judges learner runs and submits, gate attempts, build steps with preludes, IDE programs, lesson snippets and — at publish time — every reference solution of a new question. The run routes are always inline, never queued (07 amended). The catalog in backend JSON is superseded, but the files, /v1/problems and /v1/execute still ship and CI still smoke-tests them, though nothing in the web app calls them; spec §5 schedules their removal (section 7).

Evidence

1c66a0e, 9ba93c0; CI's backend-e2e job judges Two Sum in all six languages through /v1/run, plus a wrong answer, a TypeScript syntax error and an SSE check.

Decision 18 · new

One marked line per test, judged against the caller's answers

Context

Every harness printed one JSON document at exit and the service parsed all of stdout as that document. A learner's debug print() broke parsing; a run killed by TLE, MLE or a crash yielded no per-test results at all; and the server's "re-check" compared each output with the harness's own echo of the expected value — so a program that printed a fake document with output == expected and exited could pass without solving anything.

Decision

Each harness writes one marker-prefixed record per test as soon as the test finishes — flushed, with fs.writeSync in Node so it survives a kill — then a summary: \x1eCMR:{"i":0,"output":[0,1],"runNs":1200,…}. Anything on stdout without the marker is the learner's own output. The service compares every output with the expected value it holds, never with the harness's echo, honouring compareMode and a 1e-6 tolerance when the signature returns doubles. For Python, JavaScript and TypeScript the harness receives the inputs only, and the Go harness doesn't embed the answers, so they never enter the box.

Consequences

Prints are harmless; a TLE, MLE or RE keeps the results of the tests that finished, the test that was running carries the reason and later ones are "not run"; the local adapter streams records live. The residual risk: C++ and Java still embed expected values as typed literals, so the answers sit inside the compiled binary — but the verdict is still decided outside the box.

Evidence

6c1bf15; harnessProtocol.ts; the forgery is in section 6.

Decision 19 · new

TypeScript transpiled in-process; Go compiled against a warm standard library

Context

The brief asks for Python, JS/TS, Java, C++ and Go; the service had four. TypeScript needs a compiler. Go builds are slow without a cache: since Go 1.20 the standard library isn't shipped precompiled, so a cold go build recompiles runtime, fmt, … — about 3 s on a laptop and far more in a one-CPU box, against ~0.2 s warm.

Decision
  • TypeScript: typescript.transpileModule in the API process — transpile-only, types erased and not checked, like esbuild — then the JavaScript harness. A syntax error is CE with the learner's line and column. The editor agrees: Monaco's semantic diagnostics are off for TS and JS, so it never underlines code the judge accepts.
  • Go: go build in a compile box, compile-cached like C++ and Java. At startup the service warms one shared build cache and binds it read-only into compile boxes, so untrusted builds reuse the compiled standard library but can never write to (or poison) it. Run boxes get GOMAXPROCS=1 and a GOMEMLIMIT under the memory cap. The harness is generated from the signature (long → int64, double → float64, char → byte, T[] → []T); learners write bare functions, and the service hoists and deduplicates imports with //line directives so errors point at the learner's own lines.
Consequences

Six languages for questions, five for component builds (25). A type error never fails a TypeScript run — deliberately. Go's timing is process-wide (getrusage) because its standard library has no per-thread CPU clock; with one P and the main thread locked, the extra is GC and sysmon. Measured in the image: a cold build in a single-core box took ~6 s, warm ~0.1 s.

Evidence

a00cc7f, fbbe1c2, 681c82c; the Go wrapper tests build and run real binaries against Go 1.22 in CI.

Decision 20 · new

Hidden tests never leave the server

Context

A submit runs every test, hidden ones included, and streams each result live. A program can print a hidden input into its own exception message or stderr, and the per-test error text would carry it out.

Decision

The runner redacts before anything is emitted or stored: a hidden test carries no input, expected value or output, and its error is cut to the exception's class. The author's explain_on_fail note travels only with a failed test. app.test_results stores the same redacted shape, so the submission page can't leak later; reference solutions are never selected for a learner's page at all. Custom inputs on /api/run get their expected value from the reference solution, and an input the reference itself fails on is rejected.

Consequences

A learner sees pass or fail and the runtime for a hidden test — in the stream, on /submissions/[id], anywhere — and never its data. A submit on a question reachable only through a running gate attempt counts for the gate, so it can't earn the locked topics' tokens.

Decision 22 · new

An append-only token ledger, bucketed by source difficulty

Context

Solving earns topic tokens; recipes and some hints spend them; a recipe can ask for "2 Stack tokens from Medium or harder". A balance must never go negative — not under concurrent requests, not when a verdict is replayed.

Decision
  • Append-only. app.token_ledger rows are never updated or deleted (a trigger raises). A balance is SUM(amount) per (user, topic, source difficulty) — a bucket. Corrections are new admin rows.
  • Earning, once. The first accepted submit of a published question pays, per question topic, round(BASE × weight × (1 − penalty%)) with BASE 1, 2, 3 for Easy, Medium, Hard; the first passing build pays BASE for the step's difficulty. A partial unique index on (user, reason, ref, topic, difficulty) WHERE amount > 0 makes both idempotent: a replay inserts nothing. Composite questions, whose topics span tiers, are how higher-tier tokens enter.
  • Spending, never overdrawn. One transaction takes pg_advisory_xact_lock(hashtextextended(user_id, 0)), re-reads the buckets, and debits each requirement from its qualifying buckets in ascending difficulty — cheapest tokens first, buckets below the minimum skipped — one negative row per bucket touched. Any shortfall throws InsufficientTokens and nothing is written.
Consequences

Concurrency is serialized per user, not globally. The same planner feeds the map's "what's blocking you", the unlock dialog's exact debits and the Directus recipe editor's cost preview, so they can't disagree with what is charged. Tested: the planner is cross-checked against a brute-force allocator over every balance 0–2; 20 parallel spends never overdraw with the lock — and overdraw 18 of 20 without it.

Evidence

9f4d926, 28c76b8, c0a7797; web/lib/server/ledger.ts, rules/recipes.ts.

Decision 23 · new

Unlock recipes, tiers and gates

Context

Progression should resist grinding one easy topic, never dead-end, and always tell the learner exactly what to do next.

Decision
  • Tiers open through gates. Tier 0 is free: its topics are unlocked without any rows. Tier N opens only when its gate is passed: a timed attempt (45–60 min in the content) over four questions with a pass threshold of three. Eligible means tier N−1 is open, no attempt is running and any cooldown is over; a failure starts a 12–24 h cooldown (a CHECK in SQL). Attempts finish explicitly, or lazily when read after the deadline, stamped at the deadline; at most one runs per user and gate (a partial unique index). Gate questions stay reachable during an attempt even when their topics are locked.
  • Topics unlock through recipes. In an open tier, a topic unlocks by spending any one of its recipes: the spend of decision 22 plus an unlocks row, in one transaction.
  • What's blocking you. A closed tier's gate (with its eligibility or cooldown); otherwise, per recipe, missing = Σ max(0, quantity − qualifying balance), and the cheapest recipe is the smallest missing, then the smallest total quantity, then the recipe's order. The map shows it next to the questions and builds that would pay what's missing; the unlock dialog states the exact debits first.
Consequences

Content can strand learners, so it is simulated rather than trusted: the 16 recipes were tuned against an exhaustive search over every unlock order, with no dead end even for a learner who buys every token-cost hint. The seed validator refuses recipes the content can never pay for, and the Directus recipe editor refuses a change that would leave any topic impossible to unlock. A gate submit counts only for the gate (decision 20).

Evidence

Decision 25 · new

Decision 27 · new

Two seed modes: the files or the database is the source of truth

Context

All content ships as JSON under web/prisma/seed/data and is seeded in one validated transaction. Re-running the seed upserted every row from the files, silently reverting whatever staff had edited in Directus — so seeding on start was only safe on the first deploy.

Decision
  • upsert — the CLI default, for development: the files are the truth. Rows upsert by natural key, owned sets (a question's topics, a gate's questions, recipe items) become exactly the files', and children the files dropped are deleted unless learners touched them.
  • insert-missing — the web image's default, used by SEED_ON_START: the database is the truth. A row is created only when its natural key (a slug; a gate by its tier) is absent, together with everything it owns; an existing row is never updated or deleted, and nothing is added under it.

Why not merge children by key: that would re-create hints or lessons staff deleted, or add a topic to a question and change what it pays — and positional children (build steps, recipes) have no stable key to merge on.

Consequences

Deploys can seed safely: new slugs arrive, staff edits survive. Changes to existing content in the files don't reach production — make them in Directus, or reset a row with upsert on purpose. Slugs are identity, so a seeded row staff deleted comes back on the next run; retire content by unpublishing it. A new tier whose order is taken is refused and nothing is written.

Evidence

02ef8e6: tests show insert-missing leaving every content row byte-identical after staff-style edits, and a real scratch-database run with Directus edits left content.* identical in a pg_dump diff; upsert reverted them.

Decision 29 · new

Sandbox hardening: what every box gets

Context

The adapter leaned on the Docker image to make isolate usable: a g++ shim, a global relaxation of the syscall filter (file locks for every box, learner programs included), CPU pinning written by the entrypoint on its own. And several guarantees were assumptions nobody had checked: the dev adapter handed programs the server's whole environment, --core=N was believed to pin a core, and taskset was believed to bind.

Decision

The compile service builds every isolate --run command line itself, as pure functions pinned by unit tests per language and phase (isolateCommand.ts):

  • Environment: exactly PATH=/usr/local/bin:/usr/bin:/bin, HOME=/box, LANG=C.UTF-8, plus the language's own (Go: GOMAXPROCS, GOMEMLIMIT). isolate itself is started with PATH only, so INTERNAL_TOKEN reaches no sandbox process. The dev adapter gives children the same clean slate.
  • Syscall filter (--syscalls, isolate ≥ 2.7): every restriction (65535) in every box — except that a Go compile box drops file locks (65531), because go build locks its cache and runs the compiler, not learner code.
  • CPU: one CPU per run box, planned by the service and enforced twice — taskset -c, and the same plan as per-box cgroup cpusets written by the entrypoint — because a mask alone can be widened with one sched_setaffinity. The startup probe tries to widen a box and logs enforced, advisory or missing.
  • Output: --fsize 16 MB per file in run boxes (64 MB in compile boxes); hitting it is RE “Output limit exceeded (16 MB)”. The service reads at most 16 MB of stdout and 1 MB of stderr, never through a symlink.
  • A tmpfs box root: what a program writes counts against its memory cap, so a write flood is MLE, not a full disk.
  • --core=0, --cg-mem (a cgroup cap, not an address-space rlimit), per-language PID caps, and an isolate failure becomes XX instead of an empty OK.
Consequences

Proven in the privileged production image by a 26-check smoke that CI runs on every push: six languages, fork, memory and output bombs, no network, no host files, nothing writable outside /box and /tmp, four Java threads and four Go goroutines (after a widening attempt) held to CPU ≈ wall, flock refused in a Go run box. Negative controls by hand: with pinning off the same programs burn 3.95× and 4.00× CPU per wall second, and a server pinning with taskset alone logs “ADVISORY ONLY”. The host needs a plain kernel.core_pattern: a pipe handler such as apport runs for every crashing program whatever the core limit says.

Evidence

ccd64cf, 59a658e, 0c47588, bfe3899, 02598fd, aa76665, merged as 7b7fff1; lessons in section 6.

6Bugs that taught us something

The ones worth remembering, because each encodes a rule. The first seven come from the judge's first year; the rest from building the platform.

Dev mode hides production bugs — twice

npm run dev (tsx) reads problem JSON from src/; tsc never copied it to dist/, so every production deploy had a dead Problems API. Same shape in the web app: Auth.js trusts any host in development, but in production it threw UntrustedHost and the middleware failed open — the whole app was served to anonymous visitors while login returned 500.

RuleQA the production build (npm run build && npm start), not the dev server. Write security middleware to fail closed.

Never echo a lower layer's status as your verdict

Sandbox OK means "exited 0". The judge shipped it as "Accepted" for wrong answers.

RuleEvery layer derives its own status from its own evidence.

Test data must be unambiguous

Two Sum's hidden test 4 ([1,5,3,7,9], 10) had two valid pairs; a correct brute-force solution was rejected on a test the user couldn't even see.

RuleHand-check every test against the statement's promises. When a statement says "any order", the judge must honor it.

The cross product is where the bugs are

The Java harness passed on Two Sum; the new problems passed in Python. Only Java × the new problems' 10 000-element tests hit the JVM's 64 KB method limit.

RuleWhen two features land together, QA their combination, not each in isolation.

macOS is not Linux

libc++ transitively includes <unordered_map>; libstdc++ doesn't. Correct C++ solutions compiled locally and got CE on the Linux CI runner.

RuleCI must run on the deployment OS, and the harness — not the user — owns the includes.

An open redirect hides in the friendliest feature

/auth?next=<url> sent users wherever next said, including off-site, right after they typed a real password.

RuleSanitize redirect targets to same-origin paths at the single point they're read.

Stubs must compile

Java starter code with an empty body and a non-void return is a compile error — a user pressing Run on an untouched template saw CE pointing at harness line numbers.

RuleSubmit every starter verbatim in QA; it should produce WA, never CE.

Two boxes need a manifest

Compiled artifacts are copied from the compile box to the run box by name, and Java's were copied as Main.class alone — so a Solution class, or any inner class, never reached the run box. The local adapter compiles and runs in one directory, so it couldn't show this.

RuleCopy artifacts by pattern (*.class) and test on the adapter that actually copies (19c7e80).

…and a third time: a router that never commits

In a production build every catalog filter, “Clear filters” and the submissions pagination did nothing. Next 15.5's router fetched the right RSC payload (HTTP 200) and then never committed a same-path, query-only navigation under a route-level loading.tsx. next dev doesn't prefetch, so there everything worked; the same night two more production-only router races turned up in the queue and the map.

RuleRun the browser tests against next start — CI's e2e job does. A green dev server proves nothing about the router (decision 30).

A production build into a running dev server's .next

Building beside a running next dev overwrote its .next folder; the dev server then served 404s for every chunk and nothing hydrated — which looks exactly like a broken app.

RuleGive a second build its own output folder: NEXT_DIST_DIR=.next-prod (83524b8).

The machine went to sleep mid-run

A long local verification run failed partway through because the development machine went to sleep; the timeouts and dropped connections it left behind looked like product failures. Nothing in the history records it — it cost a re-run, not a commit.

RuleBefore debugging a failure in a long local run, check that the host stayed awake (caffeinate on macOS), and re-run once.

Sliding sessions re-issued the old user's cookie

The authoring e2e failed about one run in twelve: signing in as a second user in the same browser returned a fresh session cookie, yet /api/auth/session still answered as the first. The page left open from the previous step kept making requests as that user, and Auth.js re-issues the session cookie on each one (sliding expiry) — a response landing after the sign-in overwrote the new cookie. Real users can't hit it: signed-in visitors are bounced off the sign-in pages.

RuleBefore switching users in a test, park the page on about:blank and clear cookies. A flaky test is a race until proven otherwise — 30 of 30 after the fix (cb2bf69).

The server's environment leaked into user programs

The dev adapter handed every learner program the server's whole environment. That leaked host variables — credentials included — to whatever code a learner runs, and inherited settings changed program output: FORCE_COLOR made JavaScript and TypeScript print ANSI color codes, and correct answers were judged WA. In production, isolate's keeper and proxy inherited the Node process's environment, INTERNAL_TOKEN included (the program itself couldn't read it: the box's /proc hides other processes).

RuleBuild a child's environment from an allowlist, never by inheritance: PATH, HOME, LANG and the language's own variables (ccd64cf, 0c47588, 59a658e).

--core means core-dump size

Decision 03 was first implemented as isolate's --core=N, read as “pin to core N”. It is RLIMIT_CORE: boxes were allowed N KB of core file and pinned to nothing, which went unnoticed because the image happened to pin boxes on its own.

RuleCheck a sandbox guarantee from inside the sandbox, not from a flag's name. Every box now runs --core=0, and pinning is tested by trying to break it (76b54c0, aa76665).

taskset is escapable

With CPU pinning applied by taskset alone, a Go program widened its own affinity mask with one sched_setaffinity call and burned 2 s of CPU per wall second across every CPU of the host. An affinity mask is advice the process may change; a cgroup cpuset is a limit it can't.

RuleEnforce limits in a layer the program can't reach. Pinning is now a per-box cpuset, and the startup log says whether it is enforced or “ADVISORY ONLY” (59a658e, bfe3899).

Synthetic clicks vs Monaco's EditContext

Driving the editor like a user — a click to focus, then typed keys — was unreliable across platforms: Monaco (0.55, from jsDelivr) takes text input in Chromium through the browser's EditContext API, which synthetic clicks and key events from automation don't reliably drive, so a spec could type code that never reached the model.

RuleIn tests, set the editor's model through its API — monaco.editor.getEditors()[0].setValue(code) — and test typing separately if it matters (editor.spec.ts, loop.spec.ts).

A per-IP limit behind one caller is a platform-wide limit

The compile service limited execute requests to 10 per minute per source IP. Its only caller is the web server, so every learner shared one IP: the whole platform could judge 10 submissions a minute. Under autocannon, 0 of 38 000 requests succeeded past the first 10.

RuleRate-limit where identity exists. Behind a proxy or a single caller, a per-IP limit is a global one (decision 32).

A loading boundary turns notFound() into HTTP 200

With a loading.tsx above a page, Next streams the shell before the page runs; when the page then calls notFound(), the 404 page renders — with status 200. Someone else's submission and unknown lessons looked like real 404s and weren't; the e2e specs caught it by asserting the status.

RuleKeep loading boundaries out from above any page that can 404, and assert status codes in tests (2765699, 132a0de).

The judged program shared stdout with its verdict

Every harness printed one JSON document at exit, and the service parsed all of stdout. A debug print() broke parsing, a TLE lost every test's result, and outputs were compared with the harness's own echo of the expected value — so a program that printed a fake document could pass without solving anything.

RuleNever let the judged program speak for the judge: mark the harness's lines, and compare against answers the program never held (decision 18).

An address-space cap runtimes can't start under

The isolate adapter passed the memory limit as --mem, which is RLIMIT_AS. The JVM, V8 and Go reserve large virtual regions up front and couldn't even start under a 256 MB address-space cap — and the cgroup OOM kill that MLE is built on never happened.

RuleCap what you mean to cap: resident memory is a cgroup limit (--cg-mem), not an rlimit on address space (76b54c0).

Two resources from one pool deadlock

Compile boxes and run boxes came from one pool, and a request held its run box while it compiled. With as many concurrent compiled-language requests as boxes, each held a run box and waited forever for a compile box — exactly the burst the streaming endpoint invites.

RuleWhen a request holds one resource while waiting for another, give them separate pools. Compile boxes now have their own, sized to the cores (76b54c0).

Simulate the economy before shipping it

Token-cost hints first sat on tier-0 questions. In an exhaustive simulation of every unlock order, learners who bought them spent the scarce tokens that open tier 1 and stranded themselves.

RuleTreat content that moves tokens as code: simulate it (simulate_loop.py), and refuse unaffordable recipes in the seed and in the recipe editor (816f685).

A click before hydration throws the form away

The auth forms submit through a client handler with controlled, unnamed inputs. A click before hydration fell through to a native GET submit that reloaded the page and discarded what was typed — on a slow connection, a fast user just bounced.

RuleKeep submit disabled until the form has hydrated; it also makes browser tests wait for the real handler instead of racing it (d1508a2).

7What's deliberately not done yet

  • The design files are not synced into the repo (/design-sync). The spec reconstructs MVP Architecture.html and the existing design system stands in for the rest; every screen still has to be compared with its artboard, and the design files win on conflict.
  • Directus's license: on first admin login Directus 12 asks a project owner to accept its MSCL-1.0-GPL license and data processing agreement. That is the deployment owner's call; “Skip” defers it without accepting anything.
  • Java timing counts only the calling thread: work handed to other threads is missing from runUs, pinned or not.
  • The compile cache is bounded at 256 entries, not by bytes on disk; the Go build cache sits outside it.
  • Untested: amd64 builds of the web, Directus and backup images (CI builds only the backend image), the Compose stack starting in CI, and a real Hetzner Storage Box (verified against an SFTP container).
  • Legacy to remove (spec §5): /v1/execute, /v1/problems, backend/src/data/problems and CI's legacy step; compile.ts's listProblems, getProblem and execute; four files nothing imports (CatalogList.tsx, SignOutButton.tsx, components/states/index.ts, backend/src/utils/codeTemplates.ts); a stale web/README.md.
  • Scaling out: rate limits are in-process (one web instance), the Redis queue doesn't serve /v1/run, and the sandbox shares the one VPS.
  • Books and monetization from docs/authoring-v1.md — not started.

8Glossary

Harness / wrapper
The generated program around the learner's function that runs the tests, times each call and writes one marked line per test.
Adapter
The sandbox driver — isolate in production, local in development.
Box
One isolate sandbox; compiled languages use two per request (compile, run).
Meta file
isolate's machine-readable record of time, memory and exit status.
Function vs IDE mode
A function against tests (/v1/run) versus a whole program against stdin (/v1/ide/execute).
Pure executor
The compile service's contract: the caller sends code and tests; the service keeps no content.
Prelude
The learner's own earlier components, placed before their code in a build.
Signature
A question's typed parameters and return type; what lets C++, Java and Go harnesses be generated.
compareMode
Ordered (default) or unordered array comparison.
Bucket
A user's tokens of one topic from one source difficulty; balances are sums of ledger rows.
Recipe
One way to unlock a topic: items of (token topic, quantity, minimum difficulty).
Tier, gate
A group of topics; the timed exam that opens it, with a pass threshold and a cooldown.
Component, build step
A reusable function learners write; a predict or build exercise that teaches it.
Hint ladder
nudge → concept → pseudo → line → solution, each with a score or token cost.
upsert, insert-missing
The seed's two modes: the files, or the database, is the source of truth.
Internal token
The shared secret between web/ and backend/, sent as X-Codemare-Token.
Integrator
The agent that verified and merged each parallel branch (decision 36).
