1Orientation

Codemare is an online judge for DSA practice. A signed-in user picks a problem, writes a function in Python, JavaScript, C++ or Java, and gets a verdict with microsecond timing of the algorithm itself. There is also an IDE mode: a whole program run against stdin cases.

The repository is an npm workspaces monorepo with two deployable packages and one root lockfile:

  • web/ — the Next.js app the browser talks to. Owns users, sessions, submissions, the UI.
  • backend/ — the compile service. Owns running untrusted code. No database, no users.

Everything else is support: deploy/ provisions a Linux VM for the compile service, .github/ is CI, docs/ is this page and its siblings.

3Running it

Three commands from the repo root get a full local stack; the compile service falls back to an unsandboxed local adapter on any machine without isolate (all of macOS), printing a loud warning so you can't mistake it for production.

npm install       # both workspaces via the root lockfile
npm run setup     # writes web/.env.local, generates the Prisma client, pushes schema + seeds if Postgres is reachable
npm run dev       # backend :4000 (tsx watch) + web :4001 (next dev), side by side

5Data model

One Prisma schema, three concerns: Auth.js identity tables (kept verbatim to the adapter contract), the problem catalog, and submission history. Today the compile service still reads problems from JSON files; the Problem table is a seeded mirror, ready for the move described in authoring-v1.md.

7Safety rails

The guards that are in place today. Each one exists because of a specific bug or threat — the decisions page tells those stories.

Login wall, fail-closedweb/middleware.ts — everything but /auth and /api/auth requires a session; an auth error redirects instead of passing through.
Internal tokenweb/lib/compile.ts · backend/src/middleware/internalAuth.ts — timing-safe compare; production refuses to boot without a real value on either side.
Auth rate limitsweb/lib/rateLimit.ts — sign-up 5/h per IP; login 10/15 min per IP and 5/15 min per email; the form says "too many attempts" rather than "wrong password".
Execute rate limitbackend/src/middleware/rateLimit.ts — 10 execute-family requests per minute per IP, JSON 429.
Redirect sanitizercomponents/Auth/AuthForm.tsx — ?next= accepts same-origin paths only.
Sandbox limitsbackend/src/config/sandbox.ts — 10 s CPU, 256 MB, one core, per-language PID caps; compile gets 15 s / 512 MB. Code ≤ 10 KB, body ≤ 1 MB.
Production guardslocal adapter refused with NODE_ENV=production; placeholder tokens rejected; trustHost set for self-hosting.
Verdict integrityserver-side re-validation of every test; WA derived, never echoed; hidden tests blanked in API responses.

The web app has no unit tests; it is covered by typecheck, lint, the production build, and the QA passes recorded in the decisions page. CI (.github/workflows/ci.yml) runs three jobs on every push: backend build + unit tests with a JDK; an end-to-end judge smoke on a Linux runner that submits real Python/JS/C++/Java solutions and expects OK and a wrong answer to get WA; and the web typecheck/lint/build against a Postgres container.

9Status board

Working and verified

  • Judging in all 4 languages, Problems and IDE mode
  • Algorithm-only timing; compile time separated
  • Derived verdicts, unordered compare, labeled runtime errors
  • Email/password auth, login wall, rate limits, open-redirect fix
  • Submission history and profile
  • Optional Redis queue + worker (verified against real Redis)
  • 10-problem catalog, every test hand-audited
  • CI green on Linux

Built, verified only locally

  • isolate adapter path: memory-cap kills, cgroup metering, artifact copy between boxes — no Linux host with isolate has run it yet
  • deploy/install.sh and the systemd units
  • OAuth providers (no client IDs configured anywhere)

Not built

  • Catalog in Postgres + pure-executor compile contract (Phase A of authoring-v1.md)
  • Learn section; books / marketplace; monetization
  • Password reset, email verification
  • Web unit tests
  • Double-returning problems (harness tolerance vs exact re-check)

Both services with watch, from the root

Backend tsc + copy problem data into dist/, then next build

Backend unit tests (needs a JDK on PATH for the harness suite)
npm run typecheck
Both workspaces, no emit
npm run seed
Upsert the JSON catalog into Postgres
npm run worker -w backend
Standalone queue worker (needs REDIS_URL)
sudo bash deploy/install.sh
Provision a Linux VM: isolate, runtimes, service user, token, systemd unit
deploy/release.sh user@vm
Build locally, rsync, restart the service

Environment: web/.env.local (from .env.example) holds DATABASE_URL, AUTH_SECRET, COMPILE_SERVICE_URL, INTERNAL_TOKEN; the backend reads INTERNAL_TOKEN, SANDBOX_MODE, REDIS_URL, PORT. Neither env file is committed.
